# Industrial Real-Time System

A distributed industrial telemetry platform built with:

- React + TypeScript + Vite UI
- C# REST API with SignalR
- C# SQL Data service with Entity Framework and gRPC
- C# IoT Telemetry worker
- Redis, RabbitMQ, PostgreSQL

## Run the full system

Use Docker Compose to build and run all services with one command:

```bash
docker compose up --build
```

To stop it all:

```bash
docker compose down -v
```

After startup:

- UI: http://localhost:4173
- REST API: http://localhost:5100
- RabbitMQ management: http://localhost:15672

## Project layout

- `frontend/`: React + Vite UI with 3 pages
- `services/rest-api/`: C# REST API and SignalR hub
- `services/sql-service/`: C# gRPC SQL persistence service
- `services/telemetry-service/`: C# IoT telemetry worker
- `docker-compose.yml`: full stack orchestration
- `.github/workflows/ci.yml`: CI build/test pipeline
- `prompts/`: documented AI prompt usage

## Architecture

This solution is organized into clear service boundaries:

- The **UI** is a React + TypeScript app that consumes REST metadata and receives live telemetry from SignalR.
- The **REST API** is the browser gateway that consumes RabbitMQ telemetry events, forwards real-time SignalR updates, and calls the SQL service over gRPC.
- The **SQL service** is a C# persistence boundary that stores historical telemetry into PostgreSQL and serves query data.
- The **Telemetry worker** simulates sensors, writes origin state into Redis, and publishes telemetry messages into RabbitMQ.

### Data flow

- Sensor reads are generated by the telemetry worker.
- Each reading is written to Redis for fast origin-state access.
- The worker publishes telemetry events to RabbitMQ.
- The REST API consumes those events and pushes live updates to the UI via SignalR.
- The REST API also calls the SQL service over gRPC to persist historical data.

### Why these technologies

- **gRPC** provides typed service-to-service contracts between REST API and SQL service.
- **RabbitMQ** decouples producers and consumers and makes event delivery more resilient.
- **SignalR** delivers real-time telemetry to the browser without client polling.

### Stability and evolution

- Stable: the frontend gateway, event-driven architecture, and use of Redis/RabbitMQ to separate concerns.
- Evolving: persistence strategy for high-volume telemetry, sensor partitioning, and batch ingestion.

### Failure and operational considerations

- If Redis is unavailable, the system loses cached origin state but can still recover event delivery once Redis returns.
- If RabbitMQ is delayed, live updates slow down and the system should rely on current Redis values until delivery catches up.
- Service restarts should recover cleanly because state is stored externally in Redis and PostgreSQL.
- Key operational signals include queue depth, SignalR client counts, gRPC latency, Redis health, and telemetry publish rates.

## Tests

Run backend tests with:

```bash
dotnet test IndustrialRealTime.sln
```

Run the frontend build with:

```bash
cd frontend && npm install && npm run build
```

## Notes

- All UI communication uses REST or SignalR only.
- Backend services communicate only through gRPC and RabbitMQ.
- The solution is designed to support exactly 20 sensors emitting telemetry every second.
